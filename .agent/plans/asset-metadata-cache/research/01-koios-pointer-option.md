# 01 Koios as a pointer service, costed against a local chain scan

> Research note. It costs each option and records what was checked. The choice it informed has since
> been made and is recorded in the PRD under Locked Planning Decisions; this note is the evidence
> behind it, not an open question.

**Date:** 2026-09-11
**Status:** Research, complete. Koios adopted, see the PRD's Locked Planning Decisions 9 to 11

## Scope

The architecture under evaluation treats Koios as an index, not an oracle. Koios returns a pointer to
the minting transaction. The user's own `cardano-node` holds the block. The block is read locally, and
the transaction is checked to confirm it mints the asset under the claimed policy and carries the
claimed metadata. A lying index fails the local check; an unavailable index degrades rather than
corrupts. The further observation under test is that an asset under a closed native-script policy can
never be minted again, so its CIP-25 record is final and can be fetched once and cached permanently.

Against that sits the option of obtaining the same pointers with no third party at all, by scanning
the chain the user has already downloaded.

### What was measured here, and when

All network measurements were taken 2026-09-11 against `api.koios.rest` and the Mithril release
aggregator. All local measurements were taken on one WSL2 machine against a synced **preprod** chain
at `~/.local/share/Daedalus/preprod/chain`. Mainnet is not synced on this machine, so every mainnet
figure below is either quoted from a public API or extrapolated, and is labeled as such.

Registry change-rate, policy-closure and ticker-collision figures come from the corpus measurements
taken 2026-09-10 and 2026-09-11 against the token registry at commit `c9cf09f4` (7,976 mapping files)
and are cited, not re-derived.

| Price | Free | Free | ~$29.99/mo | ~$74.99/mo | Custom |

The same page states: "Public Tier, no-cost access to API services, no API keys or subscription expiry
required. 5,000 requests per day." and "Free Tier, requires registration, higher daily request limit
of 50,000 requests per day." It also notes that "API Tokens are valid across networks" and that
hit-rates are counted separately for mainnet and testnets.

A key is obtained by connecting a wallet and signing a message; the token is a JWT carried on the
request. `https://koios.rest/guide/overview.html` describes the client as optionally accompanying a
request with "a JWT payload that carries the tiering information". So the tier is asserted by the
client's token. On the public tier there is no token, so the limit there must be enforced by source
address.

That is what the enforcement looks like in the reference deployment. The HAProxy configuration that
instance operators deploy is generated by
`cardano-community/guild-operators:scripts/grest-helper-scripts/setup-grest.sh`, and contains:

```
global
  maxconn 256
frontend app
  http-request track-sc0 src table flood_lmt_rate
  http-request deny deny_status 429 if { sc_http_req_rate(0) gt 500 }
backend flood_lmt_rate
  stick-table type ip size 1m expire 10m store http_req_rate(10s)
```

Three things follow. Rate limiting is keyed on source IP (`stick-table type ip`). Refusal is a bare
`429` with no explanatory headers, which matches the observed behavior that a `200` carries no
rate-limit headers at all: a successful call returns only `date`, `content-range`, `content-length`,
`content-type` and `x-frame-options`. And a single instance accepts at most 256 concurrent
connections.

The flood limit above is the per-instance guard an operator deploys, not the cluster's daily-cap
accounting, which sits at the monitoring and proxy layer described in the overview page. Both are
published; neither publishes a per-endpoint cost.

## 2. The good-citizen question

### What the volume would actually be

Under fetch-once-per-asset, with responses trimmed by `select=` and assets batched per call, a
wallet holding K distinct assets costs **three requests, once, for the lifetime of that install**,
for any K up to the batch size. All three endpoints are bulk: `asset_info` takes an array of assets,
`tx_cbor` an array of transaction hashes, and `blocks` accepts a PostgREST `in.` filter. The Koios
FAQ advertises this explicitly: "you can query 25 transactions in a single call, only restricted by
resource and time consumption".

So the steady-state arithmetic is:

| Installs doing a cold start | Requests at the cluster |
|---|---|
| 1 | 3 |
| 1,000 | 3,000 |
| 10,000 | 30,000 |
| 100,000 | 300,000 |

Spread over the weeks in which users actually update, that is not a large number. Measured against the
5,000-per-day public tier it never binds per user, because the limit is keyed on source IP and each
user has their own. Judged on steady-state volume alone, this is defensible.

### Why the steady state is not the thing to judge

Three reasons.

**First, the failure modes ship too.** The current code is the evidence. `AssetsStore._refreshAssetsData`
iterates `this.stores.wallets.all` and calls the assets endpoint for every wallet every 60 seconds
(`ASSETS_REFRESH_INTERVAL` at `source/renderer/app/stores/AssetsStore.ts:13`). One install with five
wallets on that shape is 7,200 requests per day. A single user would exceed the public tier's daily
cap by 44 percent and land inside the Pro tier. That polling shape is what exists in the repository
today. The gap between "three requests once" and "7,200 requests a day" is one forgotten cache
invalidation, and the design that produces the second number is the one currently shipping.

**Second, a shipped binary cannot be recalled.** A server-side integration that misbehaves is fixed by
one deploy. A desktop application that misbehaves is fixed by a release that users adopt on their own
schedule, over months. The blast radius is the installed base and the correction latency is a release
cycle. A retry loop that survives review lands on every machine simultaneously, and release day
concentrates first-run traffic into a narrow window by construction.

**Third, the dependency is gratuitous.** Daedalus already runs a full `cardano-node`
with the entire chain on local disk. Every request sent to Koios asks a volunteer-operated machine to
answer a question the user's own computer can already answer. Koios instances are `cardano-db-sync`
plus PostgreSQL plus PostgREST deployments run by community operators; the FAQ states that "Instance
providers will soon be incentivised to do join the community cluster", which is to say they currently
are not. The reference deployment caps concurrency at 256 connections.

**What the judgment turns on.** The cost transferred is not volume, which is modest. It is that the
volume falls on unpaid volunteers and cannot be recalled once shipped. Set against that, Koios
answers CIP-68, which no mint scan can, and it answers CIP-25 without the largest build of the
options costed here. That is the trade, and it has been taken in favor of Koios.

Four things follow for the client, and they are what hold its volume at the steady state above rather
than at the 7,200-a-day polling shape the current code demonstrates. Requests are batched and trimmed
with `select=`. Resolution is fetch-once per asset, gated on policy closure. There is a hard local
ceiling that fails closed rather than retrying. And the endpoint is user-selectable, so an operator
running their own instance carries their own load, and a user who wants no third party at all has
somewhere to go once the local scan exists.

## 3. What `asset_info` returns, and whether it is sufficient

The schema is published at
`cardano-community/koios-artifacts:specs/fragments/schemas/asset.yaml`. Verified live against
subject `c76ef5451f551f3c06d48c46b153cb35221b507683b2e413122661b942544544` (ticker `BTED`).

### It does not carry a point

`asset_info` returns `policy_id`, `asset_name`, `asset_name_ascii`, `fingerprint`, `minting_tx_hash`,
`total_supply`, `mint_cnt`, `burn_cnt`, `creation_time`, `minting_tx_metadata`,
`token_registry_metadata` and `cip68_metadata`. It returns **no block hash, no slot and no block
height**. Neither does any other asset endpoint: `asset_history`, `policy_asset_info`,
`policy_asset_mints` and `policy_asset_list` all omit block identity entirely (`grep -n
"block_height\|abs_slot\|block_hash" asset.yaml` returns nothing).

A chain-sync point is a slot plus a block hash. `asset_info` gives a transaction hash, which is not
one. Resolution therefore always takes at least a second call.

### Two response-shape findings that change the cost

**The logo dominates the response.** The single-asset `asset_info` call returned 78,821 bytes on the
wire. Breaking down the one record it contained: 77,392 bytes are the base64 PNG in
`token_registry_metadata.logo`, 515 bytes are the CIP-25 payload, and 935 bytes are everything else.
The logo is 98.2 percent of the response.

PostgREST `select=` works on these RPC endpoints and removes it:

```
POST /api/v1/asset_info?select=policy_id,asset_name,asset_name_ascii,fingerprint,\
minting_tx_hash,mint_cnt,burn_cnt,total_supply,creation_time
```

returns **351 bytes** for the same asset, down from 78,821. Any use of this endpoint that does not
trim the response is moving two orders of magnitude more bytes than the task requires, at the
operator's expense.

**Koios strips the registry signatures.** Compare the two sources for the same subject:

| Source | Fields returned for each registry property |
|---|---|
| `tokens.cardano.org/metadata/<subject>` | `value`, `sequenceNumber`, `signatures`, plus a top-level `policy` |
| Koios `token_registry_metadata` | bare `name`, `description`, `ticker`, `url`, `logo`, `decimals` |

The direct registry call returned `policy` as hex plus `sequenceNumber` and a `signatures` array on
each of the six properties. The Koios copy has none of them: the object is flattened to values. There
is no `policy`, no `sequenceNumber`, no `signatures` key anywhere in it.

The verification chain for registry data has four steps:

1. Strip the two-byte era wrapper from `policy`, take blake2b-224 over `0x00` concatenated with the
   inner native script, and check it equals the subject's policy id.
2. Find the key hash the script requires.
3. Confirm blake2b-224 of the signing `publicKey` equals that key hash.
4. Verify the ed25519 signature over the property value.

Every input to those four steps is absent from the Koios response.

**So registry data taken from Koios cannot be verified at all.** Applying `decimals` from that source
would mean trusting the operator, which is precisely what the design sets out to avoid, and which
would make a `verified` flag mean "the server said so". If Koios is used for registry data, the
optimistic-decimals goal collapses; the registry channel must go to `tokens.cardano.org` regardless of
what happens to the CIP-25 channel.

### Two documentation inconsistencies

The path description for `asset_info` says "including **first** minting & token registry metadata",
while the field descriptions say `minting_tx_hash` is the "Hash of the **latest** mint transaction"
and `minting_tx_metadata` is the "**Latest** minting transaction metadata". These cannot both be true.
The distinction matters for any asset with `mint_cnt > 1`, because it decides whether the pointer is
stable. For an asset under a closed policy it is moot, since there is exactly one final state either
way, which is a further argument for tiering on policy closure.

`creation_time` is documented as "UNIX timestamp of the first asset mint" and so refers to a different
transaction from `minting_tx_hash` when the two differ.

### How many calls a full pointer resolution takes

`tx_info` supplies the missing fields, and `tx_cbor` supplies them **and** the raw transaction bytes in
one call. Measured for the same asset's minting transaction `98c1387a...`:

| Call | Returns | Bytes |
|---|---|---|
| `asset_info` (`select=` trimmed) | `minting_tx_hash` | 351 |
| `tx_cbor` | `cbor`, `block_hash`, `block_height`, `absolute_slot`, `tx_timestamp` | 3,251 |
| `tx_info` (all optional flags false) | `block_hash`, `block_height`, `absolute_slot`, `epoch_no`, `epoch_slot`, `tx_block_index`, `tx_size` | 1,168 |

For this transaction: `block_hash` `6ccb0f6742e2c84fa418d1647a905870d9dc2ab7df4510a09c0ff0f05464a4e4`,
`absolute_slot` 50588198, `block_height` 6754853.

That is a point for the block, and it is enough to read the block directly from the local immutable
files. It is **not** enough to retrieve the block over chain-sync. The Ouroboros Network
Specification is explicit that after `MsgIntersectFound` the server "replies with the best (newest) of
the points that it knows and updates the read-pointer accordingly", and that the client "can expect
the next update (i.e. a reply to `MsgRequestNext`) to be `MsgRollBackward`, either to the specified
point of intersection or an earlier point". The read pointer sits **at** the intersection, so the next
`RollForward` carries the block **after** it. The block at the point is never delivered.

Retrieving block B over chain-sync therefore requires the point of B's **predecessor**. `block_info`
returns `parent_hash` but not the parent's slot, so that route would need a further call. The cheaper
route is a height filter, verified live:

```
Request:  GET /api/v1/blocks?block_height=eq.6754852&select=hash,abs_slot,block_height
Response: [{"hash":"969da8d2693e1467d052a79b4d4dbbd22a14309a97164e9c5c578dcbaf061feb",
            "abs_slot":50588184,"block_height":6754852}]
Size:     159 bytes
```

**Call counts, then:**

| Goal | Calls |
|---|---|
| An unverified claim | 1 (`asset_info`) |
| A point usable against local immutable files | 2 (`asset_info`, `tx_cbor` or `tx_info`) |
| A point usable with chain-sync `FindIntersect` | 3 (add the parent-height lookup) |

All three endpoints are bulk, so these counts are per batch, not per asset.

### An intermediate rung: verify the transaction without reading the chain

`tx_cbor` returns the raw transaction. Given those bytes alone, three checks run locally with no chain
access at all. All three were executed against the live response:

```
blake2b-256(re-encoded transaction body) = 98c1387a234ed2e6a276fb55800810efa39b3f443012994747bbb019a07e0dc3
tx_hash claimed by Koios                 = 98c1387a234ed2e6a276fb55800810efa39b3f443012994747bbb019a07e0dc3   MATCH

blake2b-256(auxiliary data)  = 72d9430552edacdb348489d2ab38f769d9271a5b5dc18fb6452e34e30973f27c
transaction_body key 7       = 72d9430552edacdb348489d2ab38f769d9271a5b5dc18fb6452e34e30973f27c   MATCH

transaction_body key 9 (mint) = { c76ef5451f551f3c06d48c46b153cb35221b507683b2e413122661b9:
                                  { 42544544: 1000000000 } }
```

That establishes the bytes are self-consistent, that the metadata is cryptographically bound to that
transaction by its auxiliary-data hash, and that the transaction really does mint `BTED` under the
claimed policy.

What it does **not** establish is that the transaction was ever accepted into a block. A syntactically
valid, internally consistent transaction minting anything and carrying any metadata can be constructed
by anyone and never submitted. So this rung narrows the trust placed in Koios from "trust this
metadata" to "trust that this transaction is on chain", which is a much smaller claim but still a
claim. Closing it is exactly what the local block read buys, and nothing less does.

One implementation trap. The transaction id is blake2b-256 over the body **as
originally encoded**. Re-encoding with a CBOR library's canonical mode produced
`a7d5de28089cfdd3d7dd61134f40a20999be328312efa31cfa74905c78f9b41d`, which is wrong; the library's
default (non-canonical) encoding reproduced the correct hash. Relying on a re-encoder matching the
original by luck is not a verification strategy. An offset-preserving decoder that can hand back the
original byte range of a decoded item is the robust answer, and whichever library is chosen must be
checked for that capability before it is adopted.

## 4. Local verification mechanics

Two routes exist, and their costs differ by a wide margin. The proposal assumed the first.

### Route A: chain-sync over node-to-client

The socket is already wired. `source/main/index.ts:178-181` and `:356-359` resolve it to
`<stateDir>/cardano-node.socket` on Unix and to a Windows named pipe
`\\.\pipe\daedalus-<cluster>-cardano-node.socket` (`source/main/index.ts:131-136`, scoped by cluster so
concurrent installs do not collide). It is already passed to the Rust supervisor as
`node.socket_path` (`source/main/index.ts:397`, consumed at `watchdog/src/config.rs:18`).

The sequence is: connect, run the node-to-client handshake with a version the running node accepts,
open the chain-sync mini-protocol, `MsgFindIntersect` with the **predecessor's** point, consume the
`MsgRollBackward`, then `MsgRequestNext` to receive the target block in `MsgRollForward`.

Available TypeScript implementations:

| Package | Version | Last published | Notes |
|---|---|---|---|
| `@stricahq/ouroboros-network-js` | 1.0.1 | 2025-08-23 | Unix socket and TCP; Local Chain Sync, Local Tx Submission, Local Tx Monitor. README states "Tests: TODO" and "Examples: TODO". Networking only; needs a separate CBOR and ledger codec. Used by cardanoscan.io and Typhon Wallet |
| `@harmoniclabs/ouroboros-miniprotocols-ts` | 0.0.5-dev7 | 2025-09-17 | Has `ChainSyncFindIntersect`, `ChainSyncRequestNext`, `ChainSyncRollForward` and a node-to-client handshake CDDL. Pre-1.0, last commit 2025-09-17 |

Both are usable in principle. Neither is a comfortable dependency for a wallet: one ships no tests and
no examples, the other is on a `0.0.5-dev7` version tag and has been dormant for a year. Node's
`net.connect` handles Windows named pipes, so the platform surface is coverable, but it would have to
be tested on all three platforms rather than assumed.

The standing maintenance cost is the handshake. Node-to-client version numbers advance with node
releases, and a wallet that hard-codes a version set will fail against a node it was not built
against. That is a recurring obligation tied to every backend pin bump, not one-time work.

In Rust, `pallas-network` (crate `pallas` 1.1.1, updated 2026-06-19, 265,272 downloads) implements the
same mini-protocols and is a 1.x release with real adoption. The Rust supervisor is already in place.
It is built by crane with clippy and test checks wired into the flake (`perSystem/watchdog.nix`), and
it already ships in installers. The socket path is already passed to it, and it already speaks a
line-delimited JSON command and event protocol to the main process (`watchdog/src/protocol.rs`, driven
by `source/main/WatchdogManager.ts`). Adding a `VerifyMint` command and a matching event extends a
component that is already there rather than adding a new one.

The comparison for route A is therefore not "TypeScript versus introducing Rust", because the Rust
process is already introduced. It is an immature TypeScript protocol library in the main process
against a mature Rust protocol library in a supervisor that already ships.

### Route B: read the block straight out of the immutable database

Neither protocol library is needed, because the block can be read from the files on disk. This was
tested end to end on the local preprod chain and it works.

The immutable database stores, per chunk, a `.chunk` file of concatenated blocks, a `.primary`
slot-indexed offset table and a `.secondary` fixed-size record table. Measured locally: every full
`.primary` file is 86,409 bytes, which is one version byte plus 21,602 big-endian `uint32` entries,
and `.secondary` file sizes are exact multiples of 56 bytes (616, 560, 784, 60,480, 50,680). Chunks
span 21,600 slots, consistent with 6,092 chunks covering a preprod ledger state at slot 131,566,467.

Given a slot, the lookup is four reads. The chunk number is `slot / 21600`. Read two adjacent 4-byte
entries from `.primary` at the relative slot. Read one 56-byte record from `.secondary` at that
offset, which gives the block's offset and the header hash. Then read exactly that byte range from
`.chunk`. No socket, no handshake, no protocol version, and it works with the node running or
stopped.

Executed against the local chain, the first populated slot in chunk 3000:

```
slot 64800003, chunk 3000, block offset 0, length 864
header hash b52c74c66eac6a5451d9d3763ccc1792f0e5ef6ef8bba57e5cc329b80e9c2279
CBOR decodes to [era_tag=6, [header, tx_bodies(0), witness_sets(0), aux_map({}), invalid([])]]
header_body block_number=2449435 slot=64800003
```

That matches the Conway CDDL exactly
(`IntersectMBO/cardano-ledger:eras/conway/impl/cddl/data/conway.cddl`):

```
block =
  [ header
  , transaction_bodies       : [* transaction_body]
  , transaction_witness_sets : [* transaction_witness_set]
  , auxiliary_data_set       : {* transaction_index => auxiliary_data}
  , invalid_transactions     : [* transaction_index]
  ]
```

The header hash from the secondary index is directly comparable against the `block_hash` Koios
returned, which closes the loop: the index says where, the local file says what, and the hash says they
are the same block.

This is straightforward in TypeScript. It is file I/O and CBOR decoding, both of which Node does
natively, with no protocol library and no new process.

Three caveats:

- **The on-disk format is an internal implementation detail** of `ouroboros-consensus` with no
  stability guarantee. It can change in a node release. That is a standing maintenance obligation of
  the same order as the node-to-client handshake, differing in that a format change is silent whereas a
  handshake mismatch is loud.
- **The index semantics are undocumented and were derived empirically.** The primary index has 21,602
  entries for 21,600 slots and carries a leading sentinel, so slot `s` is described by entries
  `[s+1]` and `[s+2]`, not `[s]` and `[s+1]`. Every such detail is a place where a future node version
  can change behavior with no error raised.
- **Recent blocks are not in the immutable database.** Blocks within `k` (2160) of the tip live in the
  volatile database, a different format with a different index. Mint transactions old enough to matter
  are immutable, but the code must detect the miss and fall back rather than report absence.

### Feasibility verdict

**A single block can be read and verified from the Electron main process in TypeScript, and it does
not require Rust or Pallas.** That holds for the immutable-database route, which is plain file I/O
plus CBOR decoding. It does not hold for chain-sync, which needs a protocol implementation, and where
the mature library is the Rust one.

Reading the immutable files is cheap but fragile, because it depends on an undocumented internal
format. Reading over chain-sync is robust but needs a protocol library, and
the mature one is Rust. If the fragility of the file format is judged unacceptable, the cost is not
"add Rust", it is "extend the Rust component that already ships", which is a smaller step than the
proposal assumed.

## 5. The alternative with no third party: scan the chain once

The pointers Koios sells are derivable from data already on the user's disk. The traversal is cheaper
than a full decode, for the structural reason the CDDL above makes plain: `transaction_bodies`,
`transaction_witness_sets` and `auxiliary_data_set` are three separate top-level positions in the
block array. Mint information is `transaction_body` key 9. Witness sets, which in modern blocks carry
the Plutus scripts, datums and redeemers and therefore most of the bytes, are never needed. Auxiliary
data is a map keyed by transaction index, so it is decoded only for the indices that actually minted.

### Measured

Two 200-chunk samples from different regions of the local preprod chain, full CBOR decode in Python,
single-threaded, on this machine:

| Sample | Chunks | Bytes | Blocks | Transactions | Minting txs | Elapsed | Throughput |
|---|---|---|---|---|---|---|---|
| 03000 to 03199 | 200 | 580.9 MiB | 183,002 | 244,617 | 59,111 (24.16%) | 1.75 s | 331.5 MiB/s, 139,593 tx/s |
| 05500 to 05699 | 200 | 490.2 MiB | 164,534 | 169,238 | 43,280 (25.57%) | 1.78 s | 275.7 MiB/s, 95,190 tx/s |

Raw sequential read of 300 chunks (937,210,707 bytes) completed in 1.19 s, or 754 MiB/s, so decoding
costs roughly half the achievable I/O rate.

The full local preprod immutable database is 15.64 GiB across 6,092 chunks (18,276 files including
indices). At the measured rates that is **48 to 58 seconds** for a complete scan.

These figures are for a **naive full decode in Python**, materializing every witness set. A traversal
that skips witness sets does strictly less work.

### Extrapolated to mainnet

Mainnet is not synced on this machine, so this is arithmetic, not measurement.

The Mithril release aggregator reports for mainnet epoch 654, retrieved 2026-09-11:
`immutable_file_number` 9,143, `total_db_size_uncompressed` 234,700,137,730 bytes (218.6 GiB),
`cardano_node_version` 11.0.1. That total covers immutable, ledger and ancillary data. Applying the
locally measured preprod ratio of immutable to total chain directory (15.64 GiB of 19 GiB, 82 percent)
gives roughly **180 GiB of immutable data on mainnet**. Chunk count is consistent: mainnet tip
`abs_slot` 197,572,370 divided by 21,600 slots per chunk is about 9,147, against the aggregator's 9,143.

| Sustained throughput | One-off mainnet scan |
|---|---|
| 331 MiB/s (this machine, upper sample) | about 9 minutes |
| 276 MiB/s (this machine, lower sample) | about 11 minutes |
| 100 MiB/s (modest SSD, estimated) | about 31 minutes |
| 50 MiB/s (slow or contended disk, estimated) | about 61 minutes |

**Measured:** the decode throughput, the block and transaction counts, the preprod immutable size, the
chunk geometry, the raw read rate. **Estimated:** everything about mainnet, and every figure for
hardware other than this one machine. The two estimates that carry the most risk are the immutable
share of the mainnet total, and the assumption that mainnet decodes at a similar rate per byte. Mainnet
blocks are denser in Plutus witness data than preprod's, which favors the skipping traversal and
disfavors the full decode measured here.

The 24 to 25 percent minting-transaction rate in the preprod samples is testnet behavior and should
not be carried to mainnet. The mainnet rate is unmeasured.

### What the scan produces, and the design tension in it

The scan is incremental after the first pass. Mainnet produces on the order of 4,000 blocks a day, so
keeping current costs seconds.

The tension is in what to index:

- **Index only what the user holds.** Holdings are already available from `GET /wallets/{id}` as
  `assets.total`, so the scan can carry a hash set and keep only matches. The output is tiny. The cost
  is that acquiring a new asset later requires another full pass, because a forward-incremental scan
  cannot find an old mint.
- **Index every asset.** Complete and future-proof, but there are 11,177,037 assets on mainnet
  (planner-estimate count from `GET /api/v1/asset_list` with `Prefer: count=estimated`, returning
  `content-range: 0-0/11177037`, retrieved 2026-09-11). At a conservative 60 bytes per entry that is
  roughly 670 MB of local index.
- **Index by policy.** Materially smaller than by asset, since many assets share a policy, and
  sufficient to locate a mint. The mainnet distinct-policy count was not measured here and is a named
  gap; the local preprod samples saw 5,487 and 6,073 distinct policies per 200 chunks, which bounds
  nothing useful about mainnet.

This choice is not settled by this note and is a real piece of design work that the Koios route avoids.

### Cost comparison

The scan is more code than a Koios client, and the code is in less familiar territory. It needs
era-dependent CBOR shapes across Byron, Shelley, Allegra, Mary, Alonzo, Babbage and Conway. It needs
the chunk and index format, and resumability. It needs a first-run experience that explains a one-off
multi-minute pass without looking broken. Auxiliary data alone has three historical shapes: a bare metadata map in
Shelley, a two-element array in Allegra and Mary, and from Alonzo a CBOR tag 259 map whose key 0 holds
the metadata. The live sample confirms the modern shape, where the CIP-25 `721` payload sits two levels
down inside tag 259.

What the scan buys is that it has no external dependency at all, no terms of service to interpret, no
rate limit, no key, no operator to ask permission from, and no behavior that changes when someone
else's server changes. It also answers for every asset on the chain rather than only those Koios
chooses to index.

## 6. Coverage

The registry holds 7,976 subjects. Mainnet holds 11,177,037 minted assets as of 2026-09-11. The
registry therefore covers **0.071 percent of minted assets**.

That ratio does not describe what a user sees, because the three metadata channels answer different
questions and a user's holdings are not a uniform sample of minted assets.

| Channel | Where the data lives | Answered by local chain? | Answered by Koios? |
|---|---|---|---|
| Registry (`ticker`, `decimals`, `name`, `url`, `logo` for fungibles) | Off-chain, `tokens.cardano.org` | No. Not on chain at all | Values only, signatures stripped, so unverifiable |
| CIP-25 (NFT name, image, files) | Mint transaction auxiliary data | Yes, fully, and verifiably | Yes, as `minting_tx_metadata` |
| CIP-68 (name, image, traits) | Datum at the reference-NFT UTxO | Only via the live UTxO set, not a mint scan | Yes, as `cip68_metadata` |

Three consequences follow.

**Neither option removes `tokens.cardano.org`.** Decimals and tickers for fungible tokens exist only in
the registry. A local scan cannot produce them because they are not on the chain, and Koios can produce
only an unverifiable copy. Whatever else is decided, the registry channel stays, and it must go direct
rather than through Koios if `verified` is to mean anything.

**Neither option answers CIP-68.** A mint-transaction scan finds the mint, but CIP-68 metadata is in a
datum at a UTxO that changes whenever that UTxO is spent. Answering it locally requires querying the
current UTxO set, which is a local-state-query against the node, a third mechanism distinct from both
the block read and the scan. Koios answers it, and its answer is as fresh as the instance's `db-sync`.

**For CIP-25, both answer for effectively every asset, but on different terms.** A local scan sees
every minting transaction in the chain, so it answers for all 11.18 million assets. Koios answers for
whatever its instances have indexed, which their `db-sync` deployments make likely to be everything
as well. The difference is not breadth but dependency: the scan's coverage is a property of the user's
own data, and Koios's is a property of someone else's uptime.

### The share of a user's actual holdings, stated plainly

**This cannot be established and is not estimated here.**

What would be needed is a distribution of assets actually held by Daedalus users, broken down by
whether each asset has a registry entry, a CIP-25 payload, or a CIP-68 datum. That does not exist.
Daedalus collects no telemetry on asset holdings, and a search of the analytics event definitions
returns no asset-related event. No public dataset of wallet holdings broken down this way is known.

Two directional observations can be made without inventing a number, and both are already recorded in
the corpus work:

- The 0.48 percent per-asset annual change rate derived from registry history is an average over the
  whole registry. Assets a real user holds skew toward active projects and are likelier than average to
  update, so the rate for held assets is higher. Nobody has measured how much higher.
- Of the 11.18 million minted assets, the overwhelming majority are NFTs from large collections rather
  than fungible tokens, which is why the registry's 7,976 entries and the asset count differ by four
  orders of magnitude without either being wrong. That skew means the registry's coverage of *fungible
  tokens a user holds* is far better than 0.071 percent, and its coverage of *NFTs* is near zero by
  design, because NFTs use CIP-25 and CIP-68 instead.

No sharper figure is available from the evidence gathered here.

### A finding that limits what any of this can achieve

This bounds every option equally. 660 tickers collide across 4,256 subjects,
53 percent of the registry, against 3,913 distinct tickers. Many collisions are fully policy-bound:
`ADAGE` 27 of 27, `DRAGON` 12 of 12, `DIP` 11 of 11, `MAGA` 10 of 10, `NMKR` 5 of 5, `BTC` 4 of 4. Two
distinct policy-bound entries both claim the ticker `ADA`, neither of which can be real ADA, which is
not a native asset and has no policy id. For `WMTX` the cryptographically verified claimant is
plausibly the impostor, so a badge driven by `verified` would mark the wrong token.

Verification proves the policy that minted the token authored the metadata. It proves nothing about
whether the token is the one the user means. No choice between Koios and a local scan changes that,
because both are answering the question "what does this asset say about itself".

## Comparison

| Option | Cost to build | Cost to the user | External dependency left standing | What it cannot do | When the dependency is unavailable |
|---|---|---|---|---|---|
| **Koios as oracle, no local verification** | Smallest. An HTTP client and a cache table | One or two requests per batch of assets, at first run | Koios, fully trusted. Plus `tokens.cardano.org` for anything verifiable | Cannot make `verified` mean anything. Registry signatures are stripped, so decimals are asserted, not proven | No metadata for uncached assets. Nothing is wrong, just absent |
| **Koios pointer plus chain-sync verification in TypeScript** | Large. Three Koios calls per batch, an immature protocol library, node-to-client handshake maintenance per node bump, three-platform socket and named-pipe testing | Three requests per batch, plus a socket round trip per verified asset | Koios for pointers. Plus `tokens.cardano.org`. Plus a `0.0.x` or untested npm protocol library | Cannot verify registry data, which is not on chain. Cannot answer CIP-68 | Degrades to cached data. Verification stalls but nothing false is accepted |
| **Koios pointer plus direct immutable-file read (TypeScript)** | Moderate. Two Koios calls per batch, an index-format reader (demonstrated working here), CBOR decode, a volatile-database fallback | Two requests per batch, plus three small file reads per verified asset | Koios for pointers. Plus `tokens.cardano.org` | Same as above. Additionally cannot read blocks newer than `k` from the tip without a fallback path | Degrades to cached data. Local reads keep working regardless |
| **Koios pointer plus Pallas verification in the existing Rust supervisor** | Moderate. Two or three Koios calls per batch, a new command and event on a protocol that already exists, `pallas-network` at 1.1.1, plus the cross-process round trip | Two or three requests per batch. No new process; the supervisor already runs | Koios for pointers. Plus `tokens.cardano.org`. Pallas, which is mature | Same as above | Degrades to cached data |
| **Local one-time scan, no third party** | Largest. Era-dependent CBOR across seven eras, chunk and index traversal, resumability, an index-scope decision, first-run UX for a multi-minute pass | 9 to 11 minutes on this machine, estimated 31 to 61 minutes on slower disks, once. The chain-sync and Rust rows differ mainly in which protocol library carries the risk, and the Rust one
is the more mature library inside a component that already ships. The direct immutable-file row is the
cheapest verified option in build cost, and it pays for that with a dependency on an undocumented
on-disk format.

## The decision taken

Koios is adopted as the pointer service, with the user able to point Daedalus at another instance or,
once the local scan exists, at no third party at all. The reasoning is the owner's and is recorded in
the PRD under Locked Planning Decisions 9 to 11: Daedalus already ships external metadata
dependencies of exactly this class, in SMASH and in `tokens.cardano.org`; the registry's 7,976
subjects can never name an NFT, and Koios answers any asset on mainnet including CIP-25 and CIP-68;
and Koios is open source, so a user can run their own instance exactly as they already can for SMASH.

Three findings in this note constrain how that is built, and they hold whatever else changes.
Registry data must come from `tokens.cardano.org` regardless, because Koios strips the signatures
that make it verifiable, so Koios is additive to the registry and never a replacement for it. A
single block can be read and checked from the Electron main process in TypeScript, without Rust or
Pallas, by reading the immutable files directly, which is what makes the pointer confirmable against
the user's own chain. And the pointers are derivable from the user's own disk in an estimated 9 to 61
minutes of one-off scanning depending on disk speed, which is why the direct option is a real third
choice rather than a placeholder. Nothing here can tell a user that the token calling itself `ADA` is
not.

## Measurement gaps this note does not close

1. What share of assets a typical user holds is answerable from each channel. Unmeasurable without
   holdings data that does not exist.
2. The mainnet minting-transaction rate, and therefore the true cost of the auxiliary-data half of a
   scan. The preprod figure of 24 to 25 percent is testnet behavior.
3. The mainnet distinct-policy count, which sets the size of a policy-keyed index.
4. Whether `asset_info.minting_tx_hash` is the first or the latest mint. The Koios documentation states
   both. It matters only for assets with `mint_cnt > 1`, and the local pointer check confirms or
   rejects whichever transaction it names.
5. What share of mainnet assets sit under Plutus minting policies, which cannot be classified as closed
   or open by static analysis. The measured corpus is native-script only.
6. Scan throughput on representative user hardware. Every figure here is from one WSL2 machine with a
   fast SSD and a partly warm page cache.
