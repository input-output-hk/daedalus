Review of Iteration 1

Acceptance criteria, each against the evidence:

1. *A minter-chosen decoded name renders in a treatment visually distinct from a registry or CIP-25 name, on the token list, the send form and the transaction list.* Met. All six render sites route the name through `Asset.tsx`'s `renderPillContent`, and the spec drives the marking under the three prop shapes those surfaces actually pass rather than inferring it: `small={false}` with `metadataNameChars` for the token list, `hidePopOver small` for the send form, and the bare `asset` prop for the transaction list. The treatment is a dashed outline, italics and a muted colour, which is three channels rather than the single colour swap `.ascii` gave.

2. *An asset whose name bytes spell an existing registry ticker is distinguishable from the real one without reading the fingerprint, demonstrated with a fixture for both.* Met. Both fixtures exist and both display the text `USDC`. The decoded one lands under `assetNameMinterChosen` with `styles.minterChosenName` and a non-empty `title`; the published one lands under `assetName` with neither. The same pair is asserted at the resolver level in `assetName.spec.ts`, where the two resolve to equal `name` values and opposite `isMinterChosenAssetName` results, which is the property worth pinning.

3. *No token row in the list or the send form shows replacement characters.* Met. The 32-byte fixture renders no name element and the spec asserts U+FFFD is absent from the rendered text. The predicate rejects every byte above `0x7E`, which is a superset of the bytes that decode to U+FFFD.

4. *The predicate rejects the empty name and any byte outside `0x20` to `0x7E`, asserted per boundary.* Met. `0x1F` and `0x7F` are asserted immediately either side of the range, `0x20` and `0x7E` at the edges inside it, plus `0x00`, a high byte, a printable run with one non-printable byte in the middle, valid non-ASCII UTF-8 in both two-byte and three-byte forms, the empty string, `null` and `undefined`, an odd-length hex string, and a hex string containing non-hex characters. Fourteen cases, each asserting `null` rather than a falsy value.

5. *`yarn lint`, `yarn compile` and `yarn test:jest` pass.* Two of three met. `yarn lint` and `yarn test:jest` pass. `yarn compile` fails on four errors that fail identically at the base commit with the change stashed, so this task neither introduces nor is able to clear them. Recorded as a finding rather than a pass, and the criterion is judged against what the change is responsible for.

6. *`yarn i18n:manage` leaves the tracked artifacts unchanged on a second run.* Met.

7. *No new `@ts-ignore`.* Met.

Two things worth saying beyond the criteria.

The hex-shape check in the predicate is doing real work, not defensive decoration. `Buffer.from('55534443zz', 'hex')` returns the four bytes `USDC` rather than throwing, so a byte-range test on its own would accept a silently truncated prefix of a malformed name. That is the same impersonation the marking exists to prevent, arriving by a different route, and the spec drives it.

The decision to promote `ticker` to the first rung is implemented as the PRD and the task graph specify and its consequence is recorded in the plan's Risks: a registered token will now read `HOSKY … 1,234 HOSKY`, because `utils/formatters.ts:93-96` already appends the ticker to the formatted amount. That is a question for whoever wires the cache in, not a defect here, and it is written down rather than absorbed.

Summary: The change does what the task asked and the part of it that is a security requirement rather than a cosmetic one is the part that is most thoroughly driven. The one unmet check is unmet identically without the change.

Decision: approved
