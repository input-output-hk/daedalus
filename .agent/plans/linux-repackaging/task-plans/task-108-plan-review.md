Critiquer: Iteration 1
Timestamp: 2026-08-18T13:25:46Z

Outcome: The plan correctly separates `.deb` construction from installed-renderer certification and later migration, but it is not ready for implementation. The AppArmor contract conflicts with Ubuntu’s documented user-namespace policy, and Debian lifecycle, helper trust, launcher/update, unsupported-host, and validation semantics remain incomplete.

Blocking findings:
1. `task-108.md:31,44,97-100,145,177` requires an enforcing AppArmor profile containing only `userns,`. In enforce mode, unspecified Electron file, library, process, and IPC access is denied. Ubuntu’s documented Chromium exception instead uses `flags=(default_allow)` with `userns,`. The live probe compounds this by requiring `<exact-path> (enforce)` at `scripts/linux-chromium-sandbox-probe/main.cjs:952-971`. Resolve the exact profile mode, loaded-label representation, and probe predicate through `task-005-a` contract re-review before package implementation.
2. Mandatory `userns,` AppArmor policy on Ubuntu 22.04 is not presently credible. Canonical documents restricted unprivileged user namespaces as post-22.04 functionality, while Jammy’s AppArmor 3 parser predates the rule/default-allow contract. The plan acknowledges possible failure only after implementation (`task-108.md:177`) even though Ubuntu 22.04 is an unconditional acceptance row. Obtain a proven row-specific profile or revise the authoritative matrix first; a harmless unrelated profile does not satisfy the frozen policy requirement.
3. Exact parser-version equality (`task-108.md:31,98-99`) contradicts matrix rows that include future point/security updates. A security update changing `apparmor_parser --version` would make an otherwise compatible package upgrade fail. Freeze semantic ABI/profile requirements and reviewed compatibility ranges or exact point-release rows, while recording the observed parser version as evidence. Do not use an exact patch-version string as the lasting trust decision.
4. Debian lifecycle semantics are underspecified. “Postinst/removal lifecycle” does not define `preinst`, `postinst`, `prerm`, and `postrm` handling for `install`, `configure`, `upgrade`, `failed-upgrade`, `abort-install`, `abort-upgrade`, `remove`, and `purge`. Old and new scripts execute in mixed order during upgrade, so an old `postrm upgrade` can remove or unload newly installed state unless explicitly guarded. Define the complete state machine and prove fresh install, upgrade, downgrade policy, interrupted configuration, failed upgrade recovery, remove, purge, reinstall, and repeated `dpkg --configure`.
5. AppArmor ownership and rollback need transactional rules. The profile is generated by maintainer scripts rather than directly tracked as a normal package file, but the plan does not define behavior for a pre-existing symlink, foreign file, administrator modification, stale profile, half-configured package, or profile replacement failure. Require non-clobbering ownership/hash markers, atomic profile replacement, replace-without-unload during upgrade, cache behavior, reboot persistence, and cleanup that removes only matching package-owned content. Removal must not silently unconfine a still-running Daedalus process.
6. The helper trust boundary is incomplete. Before setting mode `4755`, verification must bind the helper to an expected hash embedded in immutable package metadata or the maintainer script, not merely a manifest selected from the same writable installed tree. Require every ancestor to be root-owned and non-writable, no symlink/hardlink escape, no unexpected SUID/SGID file or file capability anywhere in the package, and only the exact helper to become SUID. Define `dpkg-statoverride` and `nosuid` behavior and avoid claiming that metadata alone proves an effective Chromium route.
7. Unsupported-host state is not machine-consumable. Supported Debian and unsupported distributions both select `policy.kind = none`, while the stated schema records only matrix revision, cluster, policy kind, hashes, and policy identity (`task-108.md:98-100`). Add an authenticated manifest field for exact matrix row and `supported` versus `wallet-only`, with tests preventing an omitted distro from being indistinguishable from supported Debian. Coordinate the schema change with the existing probe and task-103 handoff.
8. The package-specific launch chain is not fully fixed. The live frontend invokes `electron` through `PATH` and trusts inherited `ENTRYPOINT_DIR`; the plan only says to generate flag-free content. Require every package launcher and restart entry point to derive its own `/opt/daedalus/<cluster>` root and invoke the exact packaged wrapper/executable, without PATH substitution or caller-controlled root selection. Define exact package-owned desktop and icon paths and modes, which are currently absent from the frozen layout.
9. Deferring auto-update redesign does not justify leaving the `.deb` operationally connected to the portable updater. Live code invokes `updateRunnerBin`, chmods downloaded content to `0777`, and executes it (`source/main/ipc/manageAppUpdateChannel.ts:90-97`); the Linux frontend can restart `$HOME/.daedalus/<cluster>/bin/daedalus` (`nix/internal/x86_64-linux.nix:373-381`). The `.deb` configuration must minimally disable installation of portable updates and the home-path restart seam. Task-110 can implement the final package-manager update UX, but task-108 must not ship an installable package that can switch itself back to the rejected package.
10. Package identity and reproducibility are too vague. Freeze a Debian-valid, monotonically ordered `Version`, exact control fields and dependency policy, treatment of the Ubuntu-only `apparmor_parser` requirement in a shared Ubuntu/Debian package, installed desktop paths, package checksums, and Hydra `binary-dist` exposure. Verify two clean builds are byte-identical or document and eliminate every nondeterministic archive field; successful Nix evaluation alone is not reproducibility evidence.
11. The forbidden-string check is both overbroad and insufficient. Searching every executable in the staged tree can match Chromium’s own embedded switch strings, while simple grep cannot prove a shell/config launch path never synthesizes a bypass. Restrict static checks to executable launch/configuration surfaces, parse desktop `Exec` values, and use runtime argv evidence later. Add a bounded installed-package startup smoke on each row to prove the profile and absolute launcher allow Daedalus/Electron to start, without calling that task-005-b sandbox certification.
12. Manual evidence does not adequately exercise privileged failure and recovery. The Ubuntu negative case is optional (`task-108.md:34`), failed upgrades are absent, and an unchanged wallet sentinel proves only non-mutation, not non-inspection. Require at least one real parse/load failure and one byte-distinct failed-upgrade recovery with prior profile/helper/package state preserved, followed by successful reconfiguration and snapshot rollback. Support the “no inspection” claim with maintainer-script source checks plus host-local file-access tracing or narrow equivalent evidence; otherwise narrow the claim to non-mutation.
13. CI and documentation seams remain incomplete. Name the exact `hydraJobs`/nonrequired aggregate and downloadable artifact wiring instead of only saying “Hydra/check”; Buildkite currently builds and uploads only `installer-*`. Update or explicitly disposition all current sandbox/package guidance, including `.agent/plans/mithril/research/mithril-bootstrap-client-notes.md`, not only README and `build.md`. Preserve the truthful distinction that `.bin` remains a legacy output until task-110 and is not a supported dApp-capable release artifact.

Non-blocking observations:
- `interactive_validation` is the truthful classification; five disposable-host package lifecycle rows and reviewed Ubuntu policy evidence cannot be replaced by Nix archive inspection.
- The additive `deb-installer-<cluster>` output is safer than replacing `installer-<cluster>` before task-110 updates release and auto-update consumers.
- Reusing `newBundle`, pinned `dpkg-deb`, existing cluster generation, shellcheck, and the schema-v2 probe is appropriately minimal.
- `.rpm`, SELinux, installed exact-renderer certification, runtime canary enforcement, portable migration, and guest enablement are correctly left to tasks 109, 005-b, 103, 110, and later release gates.
- Wallet state remains outside the package tree, no network fetch is planned, and production guest launch remains disabled.

Approval bar:
- Reconcile the Ubuntu AppArmor profile mode, exact loaded-label evidence, Ubuntu 22.04 feasibility, and parser compatibility policy with task-005-a and the live probe.
- Specify a complete Debian maintainer-script state machine with transactional profile/helper ownership, upgrade failure recovery, remove/purge behavior, reboot persistence, and running-process safety.
- Harden helper provenance, installed-tree permissions, manifest support-state identity, absolute launcher provenance, and package-specific auto-update disablement.
- Freeze Debian metadata, deterministic build evidence, exact CI artifact exposure, desktop layout, focused static/runtime tests, and mandatory privileged negative/recovery evidence.
- Correct the wallet-state evidence claim and synchronize all live package/sandbox documentation while preserving downstream task and release-gate boundaries.
